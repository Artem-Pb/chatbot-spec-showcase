# Table Bot — multi-platform FSM chatbot showcase

Демо-версия архитектуры, использованной в реальном клиентском проекте
(мультиплатформенный чат-бот для записи клиентов). Домен здесь — вымышленный:
бронирование столиков в ресторане «Wren & Table». Реального ресторана,
клиента и отрасли, для которых строилась исходная архитектура, здесь нет —
показывается только техническая механика.

## Какую проблему решает такая архитектура

Бизнесу нужен один сценарий диалога (выбор → информация → бронирование →
уведомление администратора), который должен работать сразу в нескольких
мессенджерах — и дальше расширяться на новые платформы без переписывания
бизнес-логики каждый раз заново. Наивный подход — писать отдельного бота под
каждую платформу — быстро превращается в дублирование одной и той же логики
диалога N раз с постепенным расхождением поведения.

Решение — платформо-независимое ядро: логика диалога (правила переходов,
что показывать на каждом шаге, когда создавать бронь) ничего не знает о
Telegram/VK/WhatsApp. Она работает с абстрактными `IncomingMessage` /
`OutgoingMessage` / `DialogContext`. Добавление новой платформы — это
только новый normalizer (payload → `IncomingMessage`) и новый sender
(`OutgoingMessage` → нативный формат платформы), без единой строчки в
`fsm/`.

## Архитектурные инварианты

1. **Логика диалога не знает о платформах.** Слова вроде `telegram`/`vk` в
   пакете `fsm/` и в `DialogService` — запрещены архитектурно.
2. **Платформенная специфика живёт только в `controller/` (приём) и
   `platform/` (отправка).** Нормализация payload → `IncomingMessage` — в
   нормализаторах. Сериализация `OutgoingMessage` → нативный формат — в
   `*Sender`.
3. **Handler ничего не отправляет и не лезет в сеть.** Handler возвращает
   `HandlerResult(OutgoingMessage, DialogState nextState)`. Отправку делает
   `MessageDispatcher`, оркестрацию — `UpdateProcessor`.
4. **Смену состояния применяет `DialogService`, а не Handler.** Handler лишь
   возвращает целевое состояние внутри `HandlerResult`.
5. **Каждый входящий апдейт идемпотентен.** Перед обработкой — проверка/
   вставка в `processed_update` с уникальным ограничением
   `(platform, external_id)`. Повтор доставки (webhook-платформы это делают)
   не создаёт вторую бронь.
6. **Контроллер отвечает платформе быстро.** Telegram ожидает `answerCallbackQuery`
   почти сразу — тяжёлая логика уходит в `UpdateProcessor` уже после ACK.

## Поток обработки

```
Платформа → *WebhookController
   ├─ верификация секрета (отклонить чужих)
   ├─ ранний ACK платформе (Telegram: answerCallbackQuery; возврат 200 OK)
   ├─ Normalizer: payload → IncomingMessage
   └─ UpdateProcessor.handle(IncomingMessage):
        ├─ ProcessedUpdateGuard: дубликат? → выход
        ├─ DialogService.process(msg) → ProcessOutcome
        │     ├─ найти/создать ChatUser
        │     ├─ найти/создать UserSession (@Version, optimistic lock)
        │     ├─ DialogRouter.resolve(state, event) → DialogHandler
        │     ├─ handler.handle(ctx) → HandlerResult(msg, nextState)
        │     └─ применить nextState, сохранить сессию
        ├─ MessageDispatcher.send(platform, outgoing)
        └─ если создана бронь → NotificationService.notifyAdmin(booking)
```

## Маршрутизация: DialogRouter

Ядро диспетчеризации — таблица `(state, eventType, value) → Handler` с
резолвером, который последовательно пробует:

1. точное совпадение;
2. префиксное совпадение по значению (`TABLE_2` → `TABLE_`, `DATE_2026-09-01` → `DATE_`);
3. глобальные команды (`/start`, `/reset`) — работают из любого состояния;
4. wildcard по событию в рамках состояния (например, `CONTACT_INPUT` принимает и `CONTACT`, и произвольный `TEXT`);
5. wildcard по состоянию целиком;
6. fallback-хендлер, если ничего не подошло.

Это позволяет держать десятки переходов в одной декларативной таблице, не
разбрасывая `if/else` по хендлерам, и добавлять новые ветки диалога, не
трогая существующие маршруты.

## Стек

- Java 17, Spring Boot 3.2 (Web + WebFlux — `WebClient` как единый HTTP-клиент
  для всех исходящих вызовов к платформам)
- Spring Data JPA / Hibernate — `UserSession` с оптимистичной блокировкой
  (`@Version`) на случай параллельных апдейтов от одного пользователя
- PostgreSQL — состояние сессии как `jsonb` (`SessionContext`), устойчиво к
  добавлению новых полей без миграции старых сессий
- Docker Compose — БД одной командой

## Что показано в демо

- Полное платформо-независимое ядро: `fsm/`, `orchestration/`, `service/DialogService`
- Одна платформенная интеграция — Telegram (`controller/TelegramWebhookController`,
  `platform/telegram/*`) как пример паттерна; для второй платформы нужен ещё один
  normalizer + sender, ядро не меняется
- Внешняя система бронирования — за интерфейсом `BookingProviderClient`
  (в демо — `StubBookingProviderClient`, генерирует слоты в памяти без
  реального провайдера; в проде подставляется реализация конкретного API)
- 12 хендлеров полного цикла: приветствие → выбор столика → информация/
  вопрос/FAQ → выбор даты и времени → сбор контакта → бронь → подтверждение
- Обработка гонки за слот: если провайдер бронирования вернул "слот уже
  занят" между показом доступного времени и подтверждением, хендлер сам
  запрашивает свежий список и предлагает пользователю выбрать заново —
  не падает и не создаёт дублирующую бронь

## Что не входит в демо

- Остальные платформы (VK, WhatsApp, Instagram) — паттерн интеграции
  идентичен Telegram, отдельно не дублируется
- Реальная интеграция с конкретным внешним провайдером бронирования —
  только интерфейс и in-memory заглушка
- Управление миграциями схемы (в проде — Liquibase); здесь для простоты
  демо — `ddl-auto: update`

## Быстрый старт

```bash
docker compose up -d          # поднимает PostgreSQL

export TELEGRAM_BOT_TOKEN=...        # нужен реальный токен бота для полного e2e
export TELEGRAM_WEBHOOK_URL=...      # публичный HTTPS-URL (например, через ngrok)
export TELEGRAM_WEBHOOK_SECRET=...

mvn spring-boot:run
```

Юнит-тесты (не требуют БД и реальных токенов):

```bash
mvn test
```

`GET /health` → `200 OK` после старта.
